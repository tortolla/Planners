# Cross-Domain Anchor Trajectories for CDAD-Planner

This document describes the anchor-trajectory construction stage for the **Cross-Domain Anchor Diffusion Planner (CDAD-Planner)** project.

The goal of this stage is to build a shared vocabulary of short-horizon future-path anchors across two different embodied domains:

1. **Autonomous driving** — Waymo front-camera corridor dataset.
2. **Ground robot navigation** — i2Nav-Robot front/left-camera corridor dataset.

The resulting anchors are used as structured trajectory priors for the planned **Cross-Domain Anchor Diffusion Planner**. Instead of generating trajectories from pure Gaussian noise, the planner starts from one of these learned cross-domain anchors and performs lightweight diffusion-based refinement.

---

## 1. Motivation

Large navigation foundation models and full diffusion planners are powerful but often heavy, data-hungry, and domain-specific. In this project, the objective is different: build a compact visual future-path planner that can work with both road-driving and ground-robot data.

The key idea is to avoid directly merging incompatible physical action spaces. Cars and ground robots have different dynamics, speeds, horizons, scales, and operating environments. Instead, both domains are mapped into a common **image-space future-path representation**:

```text
RGB image → normalized image-space future trajectory
```

A future trajectory is represented as a fixed number of 2D image points:

```text
trajectory = [(u1, v1), (u2, v2), ..., (uM, vM)]
```

These points are normalized into the range:

```text
u_norm = 2 * u / image_width  - 1
v_norm = 2 * v / image_height - 1
```

This produces a common normalized trajectory space:

```text
trajectory_norm ∈ [-1, 1]^(2M)
```

Both Waymo and i2Nav-Robot trajectories can therefore be clustered in the same coordinate system.

## 2. Role in the Full CDAD-Planner Pipeline

The full intended model is:

```text
Single RGB image
    ↓
Image encoder
    ↓
Anchor classifier
    ↓
Cross-domain trajectory anchor
    ↓
Lightweight diffusion / flow refinement
    ↓
Final image-space future trajectory
    ↓
Optional rasterization into centerline / corridor / heatmap
```

This anchor-construction notebook implements the dataset and clustering stage:

```text
Waymo + i2Nav manifests
    ↓
trajectory extraction
    ↓
normalization to image-space coordinates
    ↓
KMeans clustering
    ↓
shared anchor vocabulary
```

The produced anchor vocabulary is later used by the CDAD-Planner model.

## 5. Main Notebook

The main notebook for this stage is:

```text
build_cross_domain_anchor_trajectories_cdad_planner_cv2_kmeans.ipynb
```

This notebook performs the following steps:

1. Locates the Waymo and i2Nav-Robot corridor datasets.
2. Loads their `manifest.jsonl` files.
3. Extracts or reconstructs vector trajectories.
4. Resamples every trajectory to a fixed number of points.
5. Normalizes image-space coordinates to `[-1, 1]`.
6. Builds a combined cross-domain trajectory matrix.
7. Runs OpenCV KMeans for several candidate values of `K`.
8. Saves anchors and cluster assignments.
9. Saves metrics for anchor-count selection.
10. Produces visual previews of the anchor vocabulary.

## 6. Trajectory Representation

All trajectories are converted to a fixed-length vector with:

```python
M = 8
```

Each trajectory contains 8 image-space future points:

```text
[(u1, v1), ..., (u8, v8)]
```

After normalization, the flattened representation is:

```text
[u1_norm, v1_norm, ..., u8_norm, v8_norm]
```

with shape:

```text
[16]
```

This is the representation used for KMeans clustering and later for anchor-conditioned diffusion.

## 7. Clustering Algorithm

The notebook uses **OpenCV KMeans** instead of scikit-learn.

Reason:

```text
The environment had scikit-learn installed but failed because scipy was missing.
OpenCV was already available and provides a stable KMeans implementation.
```

Implementation:

```python
cv2.kmeans(..., flags=cv2.KMEANS_PP_CENTERS)
```

The clustering uses KMeans++ initialization and multiple attempts.

Candidate cluster counts:

```python
K_LIST = [8, 12, 16, 20, 24, 32]
```

The main selected configuration is:

```python
K = 20
M = 8
```

## 9. Selected Anchor Count: K = 20

The selected number of anchors is:

```python
K = 20
```

Rationale:

- `K=20` provides a clear improvement over `K=16`.
- RMSE decreases from `0.218541` at `K=16` to `0.202688` at `K=20`.
- The largest cluster becomes substantially less dominant: `4150 → 2753`.
- The minimum cluster size remains stable: `34` samples.
- No clusters are empty.
- Larger values (`K=24`, `K=32`) further reduce RMSE, but create very small clusters with only `6` and `5` samples respectively.
- These tiny clusters suggest over-fragmentation of rare trajectory patterns.

For the paper, the selection can be stated as:

```text
We select K=20 as a trade-off between anchor vocabulary expressiveness and cluster stability. Increasing K from 16 to 20 reduces RMSE from 0.2185 to 0.2027 while preserving non-degenerate clusters. Larger vocabularies further reduce reconstruction error but create very small clusters, suggesting over-fragmentation of rare trajectory patterns.
```

## 12. How These Anchors Will Be Used

The anchors define a trajectory prior for CDAD-Planner.

Training procedure:

```text
1. Load image.
2. Load normalized target trajectory.
3. Assign the nearest anchor ID.
4. Train an image encoder to predict anchor probabilities.
5. Train a lightweight diffusion / flow refiner to transform the selected anchor into the target trajectory.
```

Inference procedure:

```text
1. Input single RGB image.
2. Predict top-k anchors.
3. Select or sample an anchor.
4. Run a few diffusion / flow refinement steps.
5. Output final image-space trajectory.
6. Rasterize trajectory into heatmap / centerline / corridor if needed.
```

This differs from standard heavy diffusion planning because the model does not start from pure noise. It starts from a learned cross-domain trajectory prior.

---

## 13. Why Anchors Matter

Anchor trajectories provide several benefits:

1. **Compact multimodality**
   - Different future-path modes are represented as discrete anchors.

2. **Reduced diffusion burden**
   - The diffusion model only needs to refine an approximate trajectory, not generate from pure noise.

3. **Cross-domain unification**
   - Cars and robots are represented in the same normalized image-space trajectory space.

4. **Small-data stability**
   - Anchor-guided refinement is more stable than full generative trajectory modeling in a limited-data regime.

5. **Interpretability**
   - Anchors can be visualized directly as a vocabulary of future-path primitives.

## 15. Limitations

The anchors are built from logged future trajectories.

This means:

```text
They represent what the vehicle or robot did in the logs.
They are not guaranteed to be optimal.
They are not guaranteed to be safe.
They are not full traversability labels.
```

For Waymo, logged future trajectories are usually reasonable proxies because vehicles follow structured roads.

For i2Nav-Robot, logged future trajectories are weaker supervision because the robot can approach walls, cars, doors, narrow passages, and other operator-specific behaviors.

Therefore, the anchors should be described as:

```text
weak imitation-style image-space future-path priors
```

not as:

```text
optimal navigation primitives
```
